# Chuku design brief: keys, sync, daily labels, order management, access

This is the final brief for the owner. It merges the five module designs into one system, applies the doc-check results, and names what must be tested with a real token before building. Facts about the Whatnot Seller API come from developers.whatnot.com as read on 2026-11-03. Anything about Supabase or Resend limits is marked unverified where we have not read their docs.

Shared vocabulary used below:

- Shop = one Whatnot seller account, keyed by `lower(username)` from GET /users/me. The sorter already stores the slip's `From:` value as `items.shop` / `shipments.shop`, so this is the join between PDF rows and API rows (case must be normalized; see corrections).
- Key = one Whatnot personal access token (`wn_pat_tk_...`) for one shop. The token itself lives only in Supabase Vault.
- Internal user = a row in `allowed_users` with `shop` null. Sees and manages every shop. Today's team.
- Shop user = a row in `allowed_users` with `shop` set. Sees one shop. None exist yet.

## How it works

### 1. Sign-in gate for all of /tool/chuku/*

1. Move the sign-in block from `/tool/chuku/data/index.html` (createClient, `signInWithOtp`, `onAuthStateChange`, the allowed check) into two shared files: `/tool/chuku/gate.js` and `/tool/chuku/chuku.css`. Every page under `/tool/chuku/` loads them: `data/`, `keys/`, `order-management/`, and a new `/tool/chuku/index.html` landing page so the bare path is gated too.
2. On load, `gate.js` calls `sb.auth.getSession()`. No session: show the magic-link form with `emailRedirectTo = location.href`. Add `https://alire.org/tool/chuku/**` to Supabase Auth > Redirect URLs (today only the data page URL works).
3. With a session, call `rpc('my_access')`, which returns `{allowed, internal, shop, display_name}` for the caller's email. Not allowed: show today's "not on the allowed list" message and log a `signin` event.
4. Allowed: set `window.chuku = {email, internal, shop}`, draw a nav row (Data | Keys | Orders), fire `chuku:ready`. Internal users get a shop selector with "All shops". Shop users get no selector and every query adds `.eq('shop', chuku.shop)`.
5. Be honest on the page: GitHub Pages serves the HTML to anyone. The gate is UX only. The data boundary is RLS plus the Edge Function checks below. That is already true for `/data` today.

### 2. Keys page (/tool/chuku/keys)

Supabase pieces: tables `shops` and `shop_keys`, Vault, Edge Function `chuku-keys`, pg_cron daily check, `events` rows.

Schema (added to `chuku/schema.sql`):

- `shops(shop text pk /* lower(username) */, whatnot_user_id text unique, display_name text, seller_currency text, country_code text, tz text default 'America/Los_Angeles', created_at, added_by)`. Rows are created only from a GET /users/me response, never typed by hand.
- `shop_keys(id identity pk, shop text references shops, vault_secret_id uuid, token_hint text /* last 4 */, scopes_claimed text[], scopes_probed jsonb, expires_at date, status text /* ok | invalid | missing_scope | unreachable | removed */, last_checked_at, last_http_status int, last_error text, invalid_since, automation_on bool default false, recipients text[] default '{}', send_time time default '06:00', max_labels_per_run int default 150, stale_days int default 7, confirmed_spend_at timestamptz, last_sync_at, last_run_summary jsonb, added_by, added_at, removed_by, removed_at)`. Partial unique index on `(shop) where removed_at is null`. The token is never a column.
- Two security-definer wrappers owned by postgres: `store_shop_token(key_id, token) returns uuid` (Vault create or update) and `read_shop_token(key_id) returns text` (select from `vault.decrypted_secrets`). `revoke all ... from public, anon, authenticated; grant execute to service_role`. Only Edge Functions can call them. (Vault availability and function signatures on the free tier are unverified; see corrections.)
- Grants on `shop_keys`: select to authenticated under RLS; column-level update on `automation_on, recipients, send_time, shop` only. A `before update` trigger refuses `automation_on = true` unless `confirmed_spend_at` is set, recipients is non-empty, and `scopes_probed` does not show a hard failure on read:orders or read:shipments. An `after update` trigger writes `events` rows (`key_automation_on/off`, `key_recipients_changed`).

Flow for adding a key:

1. A team member pastes the token into a password input, ticks the scopes they chose in the Whatnot dashboard (the four required ones pre-ticked: read:orders, read:shipments, read:customers, write:shipments), optionally enters the expiry date they picked, and submits. The browser calls `supabase.functions.invoke('chuku-keys', {action:'add', token, scopes_claimed, expires_at})`. The token travels once, in the POST body, over HTTPS. The input is cleared on submit.
2. `chuku-keys` first builds a client with the caller's JWT and calls `rpc('is_allowed')`. `verify_jwt` alone is not enough, since any email that completes a magic link has a valid JWT. For shop users, the function later also checks that the token's username equals their shop.
3. Normalize: trim, strip a leading `Bearer `. Require prefix `wn_pat_tk_`. A `wn_access_tk_` token gets "that is an OAuth app token, not a personal access token".
4. GET `https://api.whatnot.com/seller-api/rest/v2/users/me` with `Authorization: Bearer <token>`. 401 means Whatnot rejected it. 200 returns `id, username, display_name, seller_currency, country_code`. There is no shop-name field; show `coalesce(display_name, '@'||username)`.
5. Probe scopes with two requests: GET `/orders?limit=1` and GET `/shipments?limit=1`. Record the HTTP status and whether `buyer`, `recipient` and `documents` came back null. Store the raw results in `scopes_probed`. These are hints, not proof: the docs do not say what status a missing read scope returns, and null `documents` can also mean "no label yet" (see corrections). write:shipments cannot be probed without buying a label; it stays "unverified" until the first generate_label returns 200.
6. If an active `shop_keys` row exists for this shop, return 409 naming who added it and when, and point to Replace. Otherwise: upsert `shops`, call `store_shop_token`, insert `shop_keys` with `token_hint` = last 4 characters, insert `events(kind='key_added')`. Never log the body. Strip the token from any error text.
7. The page lists `shop_keys join shops`: shop name and @username, `wn_pat_tk_...hint`, four scope pills (green ok, amber unverified or inconclusive, red failed), expiry (red if past, amber if within 7 days, "never" if blank), last check and status, last sync time, last label run summary, automation toggle, recipients chip editor, buttons Check now / Replace / Remove. Clicking a row shows its `events` history. Removed keys are under a toggle.
8. Daily check: a pg_cron job calls `chuku-keys {action:'check'}` through pg_net with a bearer secret stored in Vault. For every active key: GET /users/me. 401 sets `status='invalid'` and `invalid_since`, pauses sync and labels for that key without flipping `automation_on`, and logs `key_invalid` once. 429 or 5xx or network error sets `unreachable`, not invalid. 200 sets `ok`. Expiry, Regenerate and Delete in the Whatnot dashboard all look identical: a 401 with no error body.
9. Replace: same validation as add, then require `/users/me.id` equals the row's `whatnot_user_id` (else "this token belongs to @other, not @expected"). Update the Vault secret in place, re-probe, set `ok`, keep `automation_on` and recipients. One paste restores everything.
10. Remove: `delete from vault.secrets where id = vault_secret_id`, then soft-delete the row (`status='removed', automation_on=false, removed_by, removed_at`). The page says: "This deletes our copy. The token still works at Whatnot until the account owner deletes it in their dashboard." POST /users/disconnect is documented for app installations, not personal tokens, so it is not called.

### 3. Sync: Whatnot orders and shipments into Chuku

Supabase pieces: Edge Function `wn-sync`, pg_cron every 5 minutes via pg_net, table `sync_state`, new columns on `items` and `shipments`, RPCs `upsert_api_order` and `upsert_api_shipment`, `events` rows.

Schema changes:

- `items` gains `source text default 'pdf' /* pdf | api | both */, api_synced_at, order_status, transaction_type, show_id, buyer_id, api_created_at, api_updated_at, cancelled_at, subtotal_cents, shipping_cents, tax_cents, total_cents, discount_cents, sku, product_id, variant_id, api_shipment_id, line_count, order_day date, order_url`. `price_cents` keeps its meaning (gross item price in cents) so the existing views keep working. Money: `unit_price.amount` is a decimal string in major units, converted with `round(amount::numeric * 100)`.
- `shipments` gains `source, api_synced_at, api_shipment_id text unique (partial), status text, fulfillment_method, dropoff_due, label_url, bundled_url, bundled_url_at, commercial_invoice_url, tracking_service, last_mile_tracking, seller_paid_shipping_cents, replacement_shipment_id, required_actions jsonb, recipient_id, dashboard_url, api_created_at, api_updated_at, needs_fetch bool, collected_at, collected_by`. `buyer` becomes nullable (it needs read:customers). `pickup` is set from `fulfillment_method` so the sorter grouping keeps working.
- `sync_state(shop, resource /* orders | shipments */, phase /* backfill | live | paused */, next_cursor, backfill_floor, high_water, last_run_at, last_ok_at, last_error, failures)`.
- `status` columns are text, not Postgres enums, so an undocumented value does not break ingestion.

Flow per cron tick:

1. pg_cron calls `wn-sync` through `net.http_post` with a Vault-stored bearer. The function selects shops whose key is `ok`, orders them by least recent run, and works round-robin until it has used about 100 seconds, then exits. Every page of work saves its cursor, so a killed run resumes. (The Edge Function wall-clock ceiling is unverified; the chunking does not depend on the exact number.)
2. One HTTP helper per shop paces requests at about 100 ms spacing (limit is 10 per second per seller per app), honours `Retry-After` on 429 by sleeping once then abandoning the shop for this tick, and on 401 marks the key invalid and pauses the shop.
3. Per shop: GET /users/me. Update `shops` identity. If the username changed, rename `shop` on items, shipments, batches and events in one transaction.
4. Orders backfill: GET /orders?limit=50 (newest first, default `reverse=true`), from the saved cursor. For each order, GET /orders/{id}/items (paginate if `next_cursor` is non-null). Call `upsert_api_order`. Stop when `next_cursor` is null or the oldest order on the page is older than `backfill_floor` (default 90 days). Cost is roughly one request per order, so 10,000 orders take about 20 minutes spread across ticks.
5. Orders live: walk GET /orders newest first and stop at the first page where every order is older than `high_water - 10 minutes`. The docs say only "newest first" and do not say whether that means `created_at` or `updated_at` (see corrections). So the design does not depend on it: a bounded refresh step re-fetches GET /orders/{id} for every `pending` or `pending_fulfillment` order not synced in 6 hours (150 per tick), and a nightly pass re-walks the last 3 days regardless of `high_water`. `completed`, `cancelled` and `failed` are terminal and not refetched.
6. `upsert_api_order`: key is `items.order_number = Order.id`. This equality is unverified and is the first thing to test (see corrections and build order). Aggregate lines: `qty = sum(quantity)`, `price_cents = sum(round(quantity * unit_price * 100))`, `line_count`, product from the first line's `purchased_item.title` with the sorter's lot-strip rule, `api_shipment_id = max(shipment_id)`. On conflict update only API-owned columns; fill `product, lot, qty, price_cents, buyer, order_date` only when empty, because the slip text matches what the warehouse reads. Guard with `excluded.api_updated_at >= items.api_updated_at`. `order_day = (api_created_at at time zone shops.tz)::date`. If the order's shipment is not yet in Chuku, insert a skeleton `shipments` row with `needs_fetch=true`.
7. Shipments backfill and live use the same cursor walk on GET /shipments?limit=50. `upsert_api_shipment` matches in order: `api_shipment_id`, then `tracking = tracking_code` (a PDF-created row), then for pickups any order number among the shipment's items. When both an API row and a PDF row exist for one shipment, merge inside the RPC before writing tracking: re-point items, copy PDF-only columns (`show_title, slip_pages, batch_id, weight_oz, dimensions, buyer`), delete the PDF row. Refresh open shipments (`created, label_generated, dropped_off, in_transit`) and `needs_fetch` rows, 150 per tick. `bundled_url` is a presigned link valid up to 1 hour; it is stored only with `bundled_url_at`, and anything that needs the file re-GETs /shipments/{id} first.
8. Cancellation after a slip was printed: nothing is deleted. The row gets `order_status='cancelled'`; the revenue views add `where order_status is distinct from 'cancelled'`; `v_daily` groups by `coalesce(order_day, order_date)`. The order-management page lists it under "cancelled after slip printed" so the warehouse pulls that label.
9. Each tick writes one `events` row `kind='sync_run'` with counts, so the data page's Activity tab shows sync health next to drops and sign-ins. No separate board.
10. Webhooks are not in v1. The docs say subscriptions are configured per client app in the developer dashboard, and nothing documented lets a personal-token seller create one. The `wn-webhook` Edge Function (Standard Webhooks HMAC with the `wn_wh_` prefix stripped, dedupe on `webhook-id`, 2xx within 5 seconds) is specified in the sync module and should be built only when an OAuth app exists. Polling is complete on its own.

### 4. Daily label automation and email (per key)

Supabase pieces: tables `label_runs` and `label_jobs`, Edge Function `label-runner`, pg_cron every minute, private Storage bucket `labels`, Resend with the verified alire.org domain.

Schema:

- `label_runs(id, shop_key_id, local_date, kind /* scheduled | manual */, status /* queued | discover | enrich | needs_approval | generate | collect | assemble | sent | partial | empty | failed_auth | failed */, locked_until, counts jsonb, pdf_path, resend_id, error, started_at, finished_at)`. Unique on `(shop_key_id, local_date) where kind='scheduled'`. Unique partial on `(shop_key_id)` where status is not terminal, so one run per shop at a time.
- `label_jobs(shop_key_id, wn_shipment_id, pk on both; wn_order_ids text[], buyer_username, fulfillment, products jsonb, sku_count, wn_status, state /* candidate | ready | skipped | enqueued | fetched | timeout | cancelled | sent */, generated_by /* us | outside */, doc_path, sent_run_id, reason, first_seen, last_seen)`. This is the double-send ledger: a shipment is in exactly one emailed PDF.

Flow:

1. Every minute pg_cron calls `label-runner`. Part one: for each key with `automation_on`, `confirmed_spend_at` set, and `status='ok'`, where local time in `shops.tz` is past `send_time` and no run exists for today's local date, insert a `queued` run. "Run now" on the keys page inserts a `manual` run through RPC `request_label_run(key_id)`.
2. Part two: pick one non-terminal run with `for update skip locked`, set `locked_until = now() + 2 min`, do one bounded step (at most about 60 Whatnot calls, about 6 seconds at the rate limit), write the new status, release. A crashed step is simply re-run after the lock expires.
3. Discover: GET /shipments?limit=50 newest first until a page holds 50 consecutive shipments older than `stale_days`, or `next_cursor` is null. There is no status or date filter, so this scan is the only way. Classify each into `label_jobs`: `created` + `shipping` + never sent = candidate; `pickup` not cancelled + never sent = candidate (no label, just the slip); `label_generated` + never sent = candidate with `generated_by='outside'`; `created` older than `stale_days` = skipped "stale" and listed for a human; cancelled, failed, dropped_off, in_transit, delivered = untouched. The run therefore takes everything currently unlabeled, not only orders created on the calendar day. An order placed at 23:50 or one that sat because yesterday's run failed is not lost.
4. Enrich: per candidate, GET /shipments/{id}/items for `order_id`s, then GET /orders/{order_id}/items (cached per order within the run) for `purchased_item.title, quantity, unit_price`, and GET /orders/{order_id} to catch `cancelled` or `failed` before any money is spent. Buyer = `Shipment.recipient.username` (needs read:customers). Apply the sorter's lot-strip regex to titles. Jobs with no `purchased_item` get `sku_count 99`, exactly like the sorter's `a.products.length || 99`.
5. Guard: if this is the key's first run, or ready shipping jobs exceed `max_labels_per_run`, or the key is not `ok`, stop at `needs_approval` and email a dry-run summary with an Approve link to the order-management page.
6. Generate: for each ready shipping job with `wn_status='created'` and tracking null, POST /shipments/{id}/generate_label. 200 means enqueued, not generated. 409 ("Shipment state, settings, or seller setup prevents generation", commonly a missing dimension profile) = skipped with the dashboard URL in the email. 403 ("Seller verification required, or insufficient scope") = stop the run, set key `missing_scope`, record both possible causes. 401 = stop, key `invalid`. 429 = sleep `Retry-After`. 503 = leave ready, retry next tick, give up after 6. Never call generate_label on a shipment that already has tracking or is `label_generated`: whether a second call is a no-op, a 409 or a second purchase is undocumented. Pickups skip this step.
7. Collect: for each enqueued job, GET /shipments/{id} each tick. When status is `label_generated` and `documents.bundled_url` is non-empty, download it in the same tick (presigned, 1 hour), check the first bytes for `%PDF-`, upload to Storage at `labels/{shop}/{local_date}/{shipment_id}.pdf`, state `fetched`, record `seller_paid_shipping_cost`. If the file is not a PDF, store it and mark `fetched_nonpdf`; it is linked in the email, not merged. Worker failures are never exposed by the API, so a job still `created` 30 minutes after the last enqueue becomes `timeout` and is listed under needs attention. Tomorrow's discover sees it again.
8. Assemble: re-GET every shipment going into the PDF and drop any now `cancelled*`. Sort with the sorter's comparator ported to Deno: shipping before pickup; `sku_count` ascending; within a count, bigger pile first then A-Z by title signature; within a pile, buyer A-Z; pickups last by username. Merge with pdf-lib by `copyPages`, pages at native size, then append the Product count index page drawn like `saveSortedPdf`. Upload to `labels/{shop}/{local_date}/run-{id}.pdf` and make a 7-day signed URL.
9. Send via Resend from `labels@alire.org` to `shop_keys.recipients` with header `Idempotency-Key: label-run-{id}`. Attach the PDF when small enough; otherwise link only. (Resend's idempotency support and size limit are unverified; see corrections.) Then in one SQL statement set run status (`sent` or `partial`), `resend_id`, and `label_jobs.sent_run_id` for every included job. Zero candidates = status `empty`, no email.
10. Email body: subject "Labels {shop} - {Tue Nov 3} - 42 boxes, 3 pickups". Sections: counts by SKU count, pickups, labels bought and summed shipping cost, labels found already generated outside; product pull list; print order preview; needs attention (timeout, cancelled after purchase, 409 skipped, stale, no product title); links to `/tool/chuku/order-management?run={id}` and the signed PDF. No buyer addresses in the text.
11. After send, delete the per-shipment files from Storage. The merged PDF carries buyer addresses on the slips, so its retention is an owner decision (default 7 days).

### 5. Order-management page (/tool/chuku/order-management)

Reads the extended `items` and `shipments` tables under the same RLS as the data page. No new tables. One Edge Function `wn-action` and one RPC `mark_collected`.

1. After the gate, one supabase-js query mirroring the data page's `fetchAll()`: shipments with `source in ('api','both')` in the date range (default 30 days on `api_created_at`), with their items, filtered by shop when chosen. Pending `shipment_actions` are fetched in a second query. Item details load lazily on drill-down.
2. Derived UI state, computed client-side: needs_label (`created` + shipping, no pending action), label_requested (pending action under 30 min), label_timeout (over 30 min), label_generated, dropped_off, in_transit, delivered, failed, cancelled (three cancelled sub-statuses as one pill with the raw value in the title), cancelled_dropped (`cancelled_not_shipped_with_dropoff`, its own red pill because the parcel is in the carrier network), pickup_waiting, pickup_collected (local stamp), replaced (hidden by default), unknown (raw grey pill).
3. Overdue = `dropoff_due < now()` and the shipment is still pre-transit. Due soon = within 24 hours. `dropoff_due` is documented null for pickups and shipped parcels, so pickups show an age in days instead, never overdue.
4. Tiles: needs label, overdue, in transit, pickups waiting. No chart; the data page already charts volume. Columns reuse the data page's col tuple convention: Date, Shop (hidden with one shop), Buyer (or "hidden by scope"), Items, Status pill, Due, Tracking, Label, actions. Chips: Needs label, Labeled, Shipped, Delivered, Pickup, Problems, Replaced. Search over buyer, tracking, order numbers, shipment id, 200 ms debounce.
5. Drill-down row: items with title, SKU, qty, unit price; weight and dimensions; `required_actions` rendered raw as pills (schema unread); replacement chain followed client-side up to 10 hops with a note that `replacement_shipment_id` is only the immediate successor; Whatnot dashboard link; action log; "Seen in sorter batch #n" when a slip row matches.
6. Actions go through `wn-action`, which checks the caller's JWT with `rpc('is_allowed')`, reads the token with `read_shop_token`, inserts a `shipment_actions` row (unique partial index on pending generate_label blocks a second click), calls Whatnot, records the HTTP status and response text. Offered: Generate label (needs_label or label_timeout, confirm dialog says it buys postage with the shop's saved settings), Open label (kind `documents`: re-GET /shipments/{id}, return a fresh `bundled_url`, open in a new tab), Mark pickup collected (RPC `mark_collected`, local stamp with the clicker's email, no Whatnot call). Not offered: cancel order, void label (no endpoint found), add tracking code (request body unread; behind a flag).
7. Refresh: manual button, auto reload 3 seconds after an action, and a 45-second poll only while the tab is visible and a row is label_requested. Footer shows "Synced from Whatnot: <max(api_synced_at)>". Realtime is deferred.
8. Phone layout reuses the 640px breakpoint: secondary columns hidden, status pill carries the due text, actions move into the detail panel.

### 6. Who sees what

1. `alter table allowed_users add column shop text, add column invited_by text, add column created_at`. Existing rows stay null, so today's team keeps seeing everything the moment this runs.
2. Replace `is_allowed()` usage with small stable security-definer functions: `jwt_email()`, `is_internal()`, `my_shop()`, `can_manage(shop)`, `my_access()`. Keep `is_allowed()` defined until the data page switches to the shared gate. Grant execute to `authenticated` only.
3. Rewrite the select policies on `batches, shipments, items, events, shops, shop_keys, sync_state, label_runs, label_jobs` to one pattern: `using ((select is_internal()) or lower(shop) = (select my_shop()))`. The `(select fn())` form runs each function once per statement instead of once per row. Events with null `shop` (sign-ins) are internal-only by construction. The views are `security_invoker`, so they inherit this.
4. `allowed_users` keeps zero policies. Internal users manage it through RPCs `invite_user(email, shop, note)`, `remove_user(email)` (refuses to delete the last internal row), `list_users()`. No Supabase dashboard action is needed: `signInWithOtp` creates the auth user on first request.
5. All writes to `shops`, `shop_keys`, `allowed_users` and the automation settings go through RPCs or Edge Functions that check `can_manage(shop)`. No insert or update policies exist, the same posture as `ingest_batch` today.
6. Edge Functions run as service role and bypass RLS, so worker code always derives `shop` from the key row it is iterating, never from a request body.
7. Rollout: build the schema for shop users now (one nullable column), invite none until a shop asks. Step 4 is the whole transition.

Privacy rules every module honours: tokens exist only in Vault and Edge Function memory, and no table or event holds more than the last 4 characters; no buyer street addresses are written to tables; `Shipment.recipient` is a UserSummary (username, display_name, id), consistent with today's `buyer` column; label PDFs are the one place addresses pass through (Storage during a run, Resend after), and that is called out as a decision.

## Edge cases

| Case | What we do | Severity |
|---|---|---|
| Shop owner clicks Regenerate or Delete in the Whatnot dashboard, or the token expires. The only signal is HTTP 401 with no error body, identical in all three cases. | Any 401 on /users/me or during a run sets the key `invalid` with `invalid_since`, pauses sync and labels without flipping `automation_on`, logs `key_invalid` once, emails the owner. Replace restores everything in one paste. `expires_at` is advisory only. | high |
| Slip order number may not equal API `Order.id`. The docs define no printed order number. If it is `OrderItem.id` or a display number, every order is duplicated. | Test first with the real token: GET /orders/{slip number} for 5 orders from a dropped PDF. If 404, test whether the number is an `OrderItem.id` and add a mapping table. No backfill for any shop until confirmed. | high |
| Slip `From:` value and `/users/me.username` differ by case, or the slip prints the display name. PDF rows and API rows split into two shops. | Store `shops.shop` lower-cased, compare with `lower()` everywhere, one-time `update ... set shop = lower(shop)`. Verify one slip against one /users/me call. If the slip prints the display name, add `shops.slip_name` and match either. | high |
| Token lacks read:customers. `/users/me` and `/orders` succeed, but `recipient`, `buyer` and `documents` are null, so labels can never be fetched and buyers are blank. | Probe at add time and show an amber warning. Null is ambiguous (missing scope, no label yet, or address access not approved), so the toggle is only blocked on a hard failure; the first real run confirms. Rows render "(hidden by scope)". | high |
| 403 from generate_label is ambiguous: "Seller verification required, or insufficient scope." | Store the raw text in `last_error`, show both causes, stop the run, never mark the token invalid on 403 (only 401 does that). | medium |
| Buying labels spends the shop's money automatically. A classification bug could buy hundreds. | Five guards: automation cannot turn on until `confirmed_spend_at` is set by ticking an explicit box; the first run of every key stops at needs_approval; `max_labels_per_run`; generate_label only on `created`, tracking null, younger than `stale_days`; the email states labels bought and summed `seller_paid_shipping_cost`. | high |
| generate_label returned 200 (enqueued) but the label never appears. Worker failures are not exposed. | Poll GET /shipments/{id} per tick for 30 minutes after the last enqueue, then mark `timeout`, send the PDF without it as `partial`, list it with the dashboard URL. Tomorrow's discover retries once. | high |
| Order cancelled between label purchase and email, or after a slip was printed. | Assemble re-GETs every shipment and drops `cancelled*`, listing them as "do not ship". Cancelled orders keep their row with `order_status='cancelled'`, excluded from revenue views, shown on order-management under "cancelled after slip printed". Label cost refund is not visible in the API. | high |
| Double send: cron fires twice, a step crashes after emailing, Run now during a scheduled run, two people click Generate label. | Unique indexes on scheduled runs per day and active runs per shop; `for update skip locked`; `label_jobs.sent_run_id` ledger; Resend Idempotency-Key per run; unique partial index on pending generate_label actions. | high |
| A signed-in user who completed a magic link but is not in `allowed_users` calls an Edge Function directly with their JWT. | Every function calls `rpc('is_allowed')` or `my_access()` with the caller's JWT first. `verify_jwt` alone is not enough. | high |

## Improvements worth doing

- Alert on key failure: email the owner (Resend key as another Vault secret) in the same Edge Function run that flips a key to `invalid` or `missing_scope`. Why: nobody reopens the keys page daily, and a dead token otherwise silently stops the labels. Cost: small.
- Write API-sourced rows into the existing `items` and `shipments` tables, not separate `wn_*` tables (this brief already assumes it). Why: the data page's tiles, by-day chart and buyer and product tables then include API days without a PDF drop, which is the owner's no-isolated-metrics rule. Cost: small, mostly schema.
- Shop-level sync health card on the data page and the order page: `last_ok_at`, phase, open orders awaiting label, last error. Why: paused keys and stuck backfills surface where the team already looks. Cost: small.
- Persist raw API payloads (`api_json jsonb`) on items and shipments for 30 days. Why: several model shapes were read only as summaries; the raw body lets fields be added later without a re-backfill. Cost: small.
- Nightly reconciliation of the last 3 days regardless of `high_water` (already in the sync flow). Why: Whatnot's own docs recommend API reconciliation, and the sort key is unverified. Cost: small.
- `role` column on `allowed_users` (`viewer | manager`) and `can_manage()` requiring manager. Why: a shop can give a packer a login that sees the order page but cannot replace the key or toggle the daily job. Cost: small.
- Deep links `?shipment=<id>` and `?state=needs_label&shop=<id>` on the order page. Why: the daily email and team chat can link straight to a row. Cost: small.
- Use `Shipment.dropoff_due` to flag boxes due today at the top of the email and to override stale skipping near a deadline. Why: a late drop-off is a Whatnot penalty the print stack cannot show. Cost: small.
- Per-key daily spend cap in cents from `seller_paid_shipping_cost`, plus pause after N consecutive failed runs. Why: a count cap does not catch a dimension-profile misconfiguration that makes every label cost 3x. Cost: small.
- Fetch show titles via GET /shows/{show_id} (read:shows) into a `shows` table. Why: PDF rows carry `show_title`; API rows only have `show_id`, so by-show grouping is blank for API-first days. Cost: small.
- Product title in order-page search by loading `order_lines` eagerly. Why: 60% of viewer questions are "do you have X" and the team already searches by product on the data page. Cost: small.
- `order_lines` table keyed on `OrderItem.id` with `items` as the per-order roll-up. Why: exact product reporting and per-line SKUs for grouping; also the safe key if the slip number turns out not to be `Order.id`. Decide after the first backfill reports the share of `line_count > 1`. Cost: medium.
- Supabase Realtime on `shipments` for the loaded shop. Why: the label-requested to label-generated transition is asynchronous and the team will otherwise click Refresh. Adds a connection per tab. Cost: medium.
- Overdue digest each morning via pg_cron and Resend. Why: overdue drop-offs cost money and nobody keeps the tab open. Cost: medium.
- Second scheduled send time per key sharing the same ledger. Why: shops with afternoon shows ship twice; the ledger already makes extra runs safe. Cost: small.
- Register a Whatnot OAuth app (`wn_access_tk_`) and replace token pasting with a Connect button. Why: real revocation via POST /users/disconnect, refresh tokens instead of user-entered expiry, and one webhook subscription for every connected shop (routing by `seller_id`), which fixes the webhook gap and the collect polling. Public apps need Whatnot approval for customer-address access and OAuth token lifetime is undocumented. Cost: large.

## Corrections from the doc check

Twelve claims were checked against developers.whatnot.com. None was confirmed. Two were contradicted. The rest are unverified because the Whatnot docs are silent, and three of those are about Supabase or Resend, which the Whatnot docs do not cover at all. Where a claim was unverified the design now avoids depending on it or names the test.

- Personal-token sellers and webhooks (two claims, contradicted, medium confidence). The docs say subscriptions are "configured per client app from your developer dashboard" and events need "your app and the seller's installation" to hold the scope. Nothing lets a PAT-only seller register a URL. Change: webhook intake is removed from v1. Sync is polling plus bounded refresh plus nightly reconciliation. Label completion is detected by polling GET /shipments/{id}. The `wn-webhook` function is deferred to the OAuth-app improvement.
- Slip order number equals `Order.id` (unverified). The API defines no printed order number; one order can hold several `OrderItem`s. Change: the first task in the build order is to GET /orders/{slip number} for 5 real orders. If it fails, `items` gets a mapping to `OrderItem.id` or an `order_lines` table before any backfill.
- "Newest first" means `created_at` (unverified). The docs say only "newest first by default; set reverse=false for oldest first". Change: the sync no longer relies on the sort key; it adds the open-order refresh, the 10-minute overlap and a nightly 3-day re-walk. Test by updating an order and watching where it lands.
- GET /orders and GET /shipments return 403 without the read scope (unverified). The list operations document only 200 and 422; the only documented scope 403 is on generate_label. Change: the probe records the raw status and treats 401, 403 or an empty 200 as "cannot confirm". Test with a token created without read:orders.
- `recipient` and `documents` are null when read:customers is missing (unverified for REST; documented only for webhook payloads). Null `documents` is also natural before a label exists, and address access may be a separate approval gate for public apps. Change: the probe result is a hint; the automation toggle is blocked only on a hard failure; the first real run is the proof. Test with a token lacking read:customers against a shipment that has a label.
- GET /users/me works with a zero-scope token (unverified). The operation names no scope and documents only a 401 failure, but the dashboard may not allow an empty permission set. Change: on the first real key, create a token with no permissions and call /users/me; if that fails, document the smallest scope set that works. Handle `display_name` null.
- `bundled_url` is a PDF of slip plus label, non-null for pickups (unverified). It is documented as "Combined label and packing slip, or pickup slip URL", presigned for up to 1 hour, format unstated; the `.pdf` strings are example values. Change: collect sniffs `%PDF-`, stores non-PDF files unmerged, handles null for pickups by listing them. Test by downloading one real bundled_url for a shipping and one for a pickup shipment.
- Supabase Vault availability and function signatures (unverified; Whatnot docs do not cover Supabase). Change: build step 2 starts by running `vault.create_secret` and a security-definer read in the SQL editor before any Edge Function depends on it.
- Supabase Edge Function wall-clock and CPU limits, pg_cron and pg_net on the free tier (unverified). Change: every function does bounded steps and saves cursors, so the exact ceiling does not matter; the Whatnot rate limit (10 per second per seller, 429 with Retry-After, 5-second webhook timeout) is adopted as the binding constraint. Verify limits in Supabase's docs before the first backfill.
- Resend Idempotency-Key and the 40 MB message limit (unverified). Change: send is written so that a duplicate email is the worst case, the ledger still prevents a shipment appearing in two PDFs, and the attach threshold is a config value. Verify against Resend's API reference.
- generate_label requires write:shipments (not stated on the operation; inferred from the scope description "including generating a shipping label"). Unchanged in design, but the keys page wording says "likely needs write:shipments" and the 403 message shows both causes.

## Decisions the owner must make

1. Roll out as internal-only now with the per-shop schema in place, and invite no shop users until a shop asks. Default: yes.
2. Who may add, replace and remove keys: every allowed email or a smaller admin set. Default: every internal user for now, add a `role` column before any shop user is invited.
3. The daily run labels everything currently unlabeled and younger than the stale cutoff, not only orders created that calendar day. Default: yes, with `stale_days = 7` and stale ones listed for a human, never auto-bought.
4. Spend guardrails: first run of every key needs Approve, and `max_labels_per_run = 150`. Default: yes; approve every run for shops that are not yours.
5. Send time and timezone per shop. Default: 06:00 America/Los_Angeles for every key, editable per key.
6. Labels the shop already generated in their dashboard: include in our PDF or only list. Default: include, tagged "generated outside this run".
7. Who gets token-invalid and scope alerts. Default: the owner's email plus that shop's recipients.
8. Email when there is nothing to ship. Default: silent, run logged as `empty`.
9. Scopes to tell shops to tick when creating the token. Default: read:orders, read:shipments, read:customers, write:shipments; add read:shows if show titles in the email matter.
10. Token expiry to recommend to shops. Default: 90 days, since the daily check and one-paste Replace make re-entry cheap.
11. Retention of the merged label PDF in Storage, which carries buyer addresses. Default: 7 days, then deleted; per-shipment files deleted right after send.
12. First backfill depth per shop. Default: 90 days, after a 7-day trial compared against the last dropped PDF.
13. Cancelled orders: excluded from revenue entirely or shown as a negative on the cancellation day. Default: excluded, so past days change only when a cancellation lands.
14. Multi-line orders: per-order roll-up now, or per-line rows from the start. Default: roll-up, decide on `order_lines` after the first backfill reports the share.
15. Should the order page offer Generate label at all, given the daily run does it. Default: yes, with a confirm dialog, internal users only.
16. Historical rows when a shop removes its key. Default: stay visible; `purge_shop` exists for an explicit request.
